# AGENTS.md — Lute (S&Box) Agent Knowledge Cache

Persistent, hand-maintained notes for AI agents (Devin, GLM, etc.) working on
this repo. This exists because the coding model has **no native vision
layer** — it cannot see the S&Box editor viewport directly — and because the
S&Box C# API is new enough that models will hallucinate outdated Garry's Mod
/ early-S&Box hooks if they don't check the actual engine source first.
Read this before writing S&Box code so you don't re-discover the same APIs
every session.

## Closing the vision gap: `agent/sbox_verify.ps1`

The coding model cannot process images (even though the `read` tool accepts
PNGs, they are not actually visible to it in this setup). Do **not** rely on
literally "looking at" a screenshot. Instead, run:

```powershell
powershell -File agent\sbox_verify.ps1
```

This produces a text report (also saved to `scrap/verify_<timestamp>.txt`)
with three independent signals, each cheap to reason about as plain text:

1. **Coarse screenshot pixel analysis** — a 5x5 color grid + brightness
   histogram of the primary screen. Useful for sanity checks: an all-black
   or all-(24,24,24) viewport means nothing rendered or the editor crashed;
   a warm brown/green blob in the center quadrant is probably terrain or
   world geometry; a uniform bright color across the whole grid suggests a
   shader/texture problem. This is a coarse proxy, not real vision — don't
   over-trust exact colors, use it to catch gross failures (black screen,
   viewport not visible, etc).
2. **Editor log tail** (`sbox-public-clean/game/logs/sbox-dev*.log`) — the
   most reliable signal. Every `LuteGame`/`LuteWorld`/`LuteTerrainGenerator`
   `Log.Info(...)` call shows up here with a timestamp, so you can confirm
   code actually ran (not just compiled). Lines matching
   `error|exception|fail` are auto-flagged at the bottom of the report.
3. **Scene file dump** — parses the active `.scene` JSON and prints every
   GameObject's name, world position, and component types, indented by
   hierarchy. This is ground truth for "where is everything", independent
   of whether it's rendering correctly — use it to catch objects spawned
   out of bounds, missing components, or wrong parenting.

Run this after every terrain/world-generation change, before declaring a
build "done". Compare `Lute: ...` log lines' timestamps to confirm your
latest code (not a stale build) actually executed.

## Closing the vision gap: MCP spatial probing (`agent/sbox_eyes.py`)

The S&Box editor ships a built-in MCP (Model Context Protocol) server at
`http://127.0.0.1:7269/mcp` (on by default, Editor → Preferences → MCP
Server). It exposes scene query tools as JSON-RPC — `find_game_objects`,
`get_game_object`, `scene_trace` (raycast), `play_start`/`play_stop`,
`read_console`, `editor_status`, etc. See `game/addons/tools/Code/Mcp/`
for the full toolset source, and `docs_cache/api_signatures.md` (MCP
Tools section) for the scraped signatures.

`agent/sbox_eyes.py` wraps these calls into a single script:

```powershell
python agent\sbox_eyes.py                      # full report of all objects
python agent\sbox_eyes.py Acropolis            # focus on a named object
python agent\sbox_eyes.py Acropolis --rays 9   # more ground-probe rays
python agent\sbox_eyes.py --list-tools          # show available MCP tools
python agent\sbox_eyes.py --trace "0,0,5000" "0,0,-5000"  # single raycast
python agent\sbox_eyes.py --find Acropolis      # find by name
```

Key tools for spatial reasoning (all return text, not images):
- `scene_trace` — cast a ray from A to B, returns hit point, normal,
  distance, and the GameObject/Component hit. This is how you check
  "is the monument sitting on the ground" without being able to see it.
- `find_game_objects` — search by name/component/tag, returns GUIDs.
- `get_game_object` — full details: world position, rotation, scale,
  components, children. Pass `includeComponentProperties=True` for
  serialized property values.
- `play_start` / `play_stop` — control play mode remotely. Runtime-spawned
  objects (like the Acropolis) only exist while playing.

**MCP tools only see runtime objects when play mode is running.** Static
scene objects (in the .scene file) are always visible, but anything
spawned by `LuteWorld.Build()` only exists after `play_start`.

The agent model still cannot process images — `read` on a PNG returns
"Images not shown since the current model does not support them." So
`editor_camera_screenshot` and `camera_screenshot` are useless to this
agent. Use `scene_trace` and `get_game_object` for spatial verification
instead.

### Known PowerShell/JSON gotcha

S&Box scene files use `"__type"` as the component type-discriminator key.
**`ConvertFrom-Json` silently drops this key**, and
`System.Web.Script.Serialization.JavaScriptSerializer` throws
(`Value cannot be null. Parameter name: type`) trying to parse it — both are
.NET JSON deserializer conventions where `__type`/`$type` is reserved for
polymorphic type hydration. Work around it by renaming the key before
parsing:

```powershell
$raw = (Get-Content $scenePath -Raw) -replace '"__type"', '"_ObjType"'
$json = $raw | ConvertFrom-Json
# now $component._ObjType works
```

`sbox_verify.ps1` already does this — copy the pattern if you write your own
scene-parsing script.

## S&Box API notes (from engine source, verified against this repo's usage)

### Component model

- Gameplay entities are `GameObject`s with `Component` subclasses attached.
- Lifecycle hooks: `OnStart()`, `OnUpdate()`, `OnFixedUpdate()`, `OnEnabled()`,
  `OnDisabled()`, `OnDestroy()`.
- `[Property]` exposes a field/property to the editor inspector.
- `[RequireComponent]` auto-adds/requires a sibling component (see
  `LutePlayer.Controller`).
- Networking: `[Sync]` on a property replicates it; `[Broadcast]` marks an
  RPC method. (Not yet used in this repo — `LutePlayer`/`LuteWorld` are
  currently single-player/local; add these when multiplayer lands per PRD §5.1.)
- `Scene.CreateObject(true)` creates a new GameObject in the active scene.
  `go.SetParent(parent)`, `go.WorldPosition`, `go.WorldRotation`,
  `go.WorldScale` control the transform.
- `Components.GetOrCreate<T>()` on a Component/GameObject fetches or adds a
  sibling component (used in `LuteGame.OnStart` and `LuteWorld.Build` to
  attach `LuteWorld`/`LuteTerrainGenerator`).

### Terrain (`Sandbox.Terrain` + `Sandbox.TerrainStorage`)

Source: `engine/Sandbox.Engine/Scene/Components/Terrain/Terrain*.cs`,
`engine/Sandbox.Engine/Resources/Terrain/TerrainStorage.cs`.

- `Terrain` is a `Collider` component (`IsConcave = true`). Attach with
  `go.AddComponent<Terrain>()`.
- `TerrainStorage` is a `GameResource` holding the actual heightmap/control
  map data. Create at runtime with `new TerrainStorage()` — it defaults to
  512 resolution, 20000 world-unit size, 10000 world-unit height.
  - `storage.SetResolution(int)` reallocates `HeightMap` (`ushort[]`) and
    `ControlMap` (`uint[]`) to `resolution * resolution`.
  - `storage.TerrainSize` — world units across one side (square terrain).
  - `storage.TerrainHeight` — world units of max height; raw heightmap value
    `ushort.MaxValue` maps to exactly this height.
  - `storage.HeightMap[y * resolution + x] = (ushort)value` — direct CPU
    write, row-major.
- Assign `terrain.Storage = storage;` — this triggers `Terrain.Create()`
  internally (allocates GPU textures, builds the collider) as long as the
  component is `Active`.
- **After manually writing to `storage.HeightMap`/`ControlMap` at runtime,
  you must manually push the change**:
  ```csharp
  terrain.SyncGPUTexture();  // CPU heightmap/controlmap -> GPU textures
  terrain.UpdateCollision(
      Terrain.SyncFlags.Height,           // or .Control, or both (flags)
      new RectInt(0, 0, resolution, resolution));  // dirty region
  ```
  `SyncGPUTexture()` and `UpdateCollision()` are the two calls the editor's
  own brush tools use after painting (see `BaseBrushTool.cs`,
  `PaintTextureTool.cs` for the canonical pattern this repo's
  `LuteTerrainGenerator.cs` follows).
- `CompactTerrainMaterial` packs base/overlay texture id + blend factor +
  hole flag into one `uint` for the control map (5+5+8+1 bits). Only
  relevant if painting terrain materials, not needed for heightmap-only
  generation.

### Noise (`Sandbox.Utility.Noise`)

Source: `engine/Sandbox.System/Math/Noise.cs`, `NoiseField.cs`.

- Two APIs: **static convenience functions** (not thread-safe, shared state)
  and **field objects** (thread-safe, more configurable). Prefer field
  objects for anything beyond a one-off sample.
- Static: `Noise.Perlin(x, y[, z])`, `Noise.Simplex(x, y[, z])`,
  `Noise.Fbm(octaves, x, y, z)` — all return `[0, 1]`.
- Field objects — `using Sandbox.Utility;`:
  ```csharp
  var field = Noise.PerlinField(new Noise.FractalParameters(
      Seed: 5633, Frequency: 0.001f, Octaves: 4, Gain: 0.5f, Lacunarity: 2f));
  float n = field.Sample(worldX, worldY);  // [0, 1]
  ```
  - `Noise.PerlinField(...)`, `Noise.SimplexField(...)`, `Noise.ValueField(...)`.
  - Pass a plain `Noise.Parameters` (Seed, Frequency) for single-octave, or
    `Noise.FractalParameters` (adds Octaves, Gain, Lacunarity) for layered
    fractal noise — this is what you want for terrain (see
    `LuteTerrainGenerator.cs` for a 3-layer continent/hills/detail blend).
  - `INoiseField.Sample(x, y)` / `Sample(x, y, z)` / `Sample(Vector2)` /
    `Sample(Vector3)` — always returns `[0, 1]`.

### PlayerController

- Built-in `Sandbox.PlayerController` handles WASD movement, sprint, jump,
  mouse-look, ground detection. **Don't replace it** — extend behavior via a
  sibling component (`LutePlayer` does this for spell-casting/noclip input).
- `[RequireComponent] public PlayerController Controller { get; set; }` on
  your extension component auto-wires the reference.
- `Controller.EyeAngles`, `Controller.WorldPosition`, `Controller.GetComponent<T>()`
  (e.g. to reach the `Rigidbody` for custom noclip flight — see `LutePlayer.ApplyNoclip`).

### Scene file format (`.scene`)

- Plain JSON. Root: `{ "__guid": ..., "GameObjects": [ ... ] }`.
- Each GameObject: `Name`, `Position` (string `"x,y,z"`), `Rotation`
  (quaternion string `"x,y,z,w"`), `Scale`, `Tags`, `Enabled`, networking
  fields (`NetworkMode`, etc.), `Components` (array), `Children` (array,
  recursive).
- Each Component: `__type` (fully-qualified type name, e.g.
  `"Sandbox.DirectionalLight"` or a bare project type name like
  `"LuteGame"`), `__guid`, `__enabled`, plus all its `[Property]` fields.
  **See the PowerShell gotcha above before parsing this with
  `ConvertFrom-Json`.**

### Input

- `Input.Pressed("action")` / `Input.Down("action")` check bound actions.
- Action names are defined in `sbox/ProjectSettings/Input.config`.
- `Input.AnalogMove` gives the raw WASD vector for custom movement (see
  `LutePlayer` noclip).

### FBX / model import (`.vmdl`)

Source: `engine/Sandbox.Tools/Utility/CreateModelFromMeshDialog.cs`,
`engine/Sandbox.Tools/Utility/CreateSingleModelFromMeshDialog.cs`,
`engine/Definitions/modeldoc/ModelDocApp.def`, and verified `.vmdl` files
in `game/addons/citizen/Assets/models/`.

- S&Box imports FBX meshes via a `.vmdl` file containing a `RenderMeshFile`
  node that references the `.fbx` path. The editor's "Create Model from Mesh"
  dialog generates this automatically, but you can also write the `.vmdl`
  by hand (KV3 text format).
- **Import scale**: `import_scale` in the `RenderMeshFile` node converts
  FBX units to S&Box units (inches). Common values:
  - `1.0` — FBX units are already in inches/unitless (1 FBX unit = 1 S&Box unit)
  - `0.3937` — FBX authored in centimeters (1 cm = 0.3937 inches)
  - `39.37` — FBX authored in meters
  - The FBX `UnitScaleFactor` header says 1.0 by default (meaning cm) but
    many assets are actually authored in inches/unitless — **always verify
    the imported bounding box via `model.Bounds` in code rather than
    trusting the UnitScaleFactor**.
- **Material name gotcha**: FBX files exported from some DCC tools have
  auto-generated material names like `root.0.0`, `root.1`, `root.2`, etc.
  The S&Box resource system rejects these because the dots make it parse
  the last `.N` as the file extension (expects `.vmat`). Creating `.vmat`
  files with those names does NOT help — the engine rejects the resource
  name before looking for the file.
  - **Fix**: In the `.vmdl`, add a `MaterialGroupList` →
    `DefaultMaterialGroup` with `use_global_default = true` and
    `global_default_material = "materials/dev/primary_white.vmat"` (or any
    valid `.vmat` path). This makes the engine fall back to a single
    material for all unresolvable FBX material names.
  - **Also**: Set `renderer.MaterialOverride = Material.Load("...")` in code
    to force a material at runtime, bypassing the FBX material names entirely.
- **`.vmdl` structure** (minimal, for FBX import with collision):
  ```
  rootNode → RootNode
    children:
      MaterialGroupList → DefaultMaterialGroup
        (use_global_default=true, global_default_material="...vmat")
      RenderMeshList → RenderMeshFile
        (filename="models/.../foo.fbx", import_scale=1.0, name="LOD0")
      PhysicsShapeList → PhysicsHullFromRender
        (faceMergeAngle=20.0, maxHullVertices=32)
  ```
- **Compiling**: After creating/editing a `.vmdl`, the editor's asset
  watcher will auto-recompile it to `.vmdl_c`. If the editor doesn't detect
  the change (file added externally), touch the file's LastWriteTime or
  right-click → Recompile in the asset browser.
- **Bounding box check**: `Model.Load("path.vmdl").Bounds` gives
  `Bounds` with `.Mins`, `.Maxs`, `.Center`, `.Size` in S&Box units.
  Divide by `39.37f` to get meters.

### Colliders / model collision

Source: `engine/Sandbox.Engine/Scene/Components/Collider/ModelCollider.cs`,
`.../BoxCollider.cs`, `.../Collider.cs`.

- A `Collider` component with **no sibling `Rigidbody`** becomes a static
  collider (world geometry you stand on — e.g. `WorldGround`'s `BoxCollider`,
  the Acropolis's `ModelCollider`). Add a `Rigidbody` sibling only for
  dynamic/moving bodies.
- **`ModelCollider`** — uses a `Model`'s compiled physics data
  (`Model.Physics.Parts`: hulls, meshes, spheres, capsules). One-liner to
  make an imported monument solid:
  ```csharp
  var collider = go.AddComponent<ModelCollider>();
  collider.Model = model;  // same Model as the ModelRenderer
  ```
  If `Model.Physics` is null or `Parts.Count == 0`, the collider is empty
  (no collision) — log `Model.Physics?.Parts.Count` to diagnose. A
  `PhysicsHullFromRender` node in the `.vmdl` compiles to a single convex
  hull (verified on the Acropolis: 1 part, hulls=1). Good for "is it solid";
  NOT walkable for stairs/terraces because one convex hull over a whole
  monument makes the base a vertical wall — use concave
  `PhysicsMeshFromRender` or multi-hull for walkable complex geometry.
- **`BoxCollider`** — `Scale` and `Center` are **absolute world-unit
  sizes**, not multipliers of the default 50-unit box. To get a 100×100×10
  box, set `Scale = new Vector3(100, 100, 10)` directly (not `(2,2,0.2)`).
- **Runtime collision probe** — use the MCP `scene_trace` tool (ray from A
  to B) to check what a downward ray hits: hit point, normal, distance, the
  GameObject + Component hit. This is how the agent verifies "did the
  collider actually attach" without being able to see the viewport. A ray
  that passes through your object and hits `WorldGround` at z=0 means no
  collision; a ray that stops on your object's `ModelCollider`/`BoxCollider`
  means it worked.

### MeshComponent runtime gotcha (CRITICAL)

Source: `engine/Sandbox.Engine/Scene/Components/Mesh/MeshComponent.cs`.

`MeshComponent` is an "editable polygon mesh with collision" — but its
`RebuildMesh()` **bails early when `!Scene.IsEditor`**. So at runtime (play
mode), setting `meshComp.Mesh = mesh` does NOT build the `Model` — `Model`
stays null and the block is **invisible AND non-solid**. (The earlier
builder-NPC "PASSED" test was a false positive: the NPC was grounded on
`WorldGround` beneath the blocks, not on the blocks.)

**Fix** — create the block GameObject disabled, set the mesh, then enable:
```csharp
var go = Scene.CreateObject( false );        // disabled!
// ...set name/parent/transform...
var meshComp = go.AddComponent<MeshComponent>();
meshComp.Collision = MeshComponent.CollisionType.Mesh;
// ...build PolygonMesh, assign material...
meshComp.Mesh = mesh;
go.Enabled = true;                           // triggers OnEnabledInternal -> RebuildRenderMesh
```
`OnEnabledInternal()` calls `RebuildRenderMesh()` with **no `!IsEditor`
guard**, so it builds the `Model` (render + physics) from the now-set
`Mesh`. `CreateObject(true)` would enable first (with `Mesh=null`), so the
rebuild never happens. This pattern is used in `LuteWatchtower.PlaceBox`
and `LuteBuilderNpc.PlaceBlock`.

- A `MeshComponent` with `Collision=Mesh` is a concave collider
  (`IsConcave = true`) — good for terrain/static world geometry. Use
  `Collision=Hull` for a convex approximation, `Collision=None` for
  render-only.
- For walkable stairs, each step must be a **solid block from the ground up
  to its tread** (not a thin floating tread) and each riser must be ≤
  `PlayerController`'s `StepUpHeight` (18 units ≈ 0.46m). See
  `LuteWatchtower.BuildStair`.

## Closing the vision gap: live agent control via MCP

The agent can drive an in-game body live through the S&Box native MCP
endpoint (`http://127.0.0.1:7269/mcp`) — this is the closest thing to
"being in the world" for a vision-less agent. Pattern (verified on
`LuteBuilderNpc`):

1. **Expose control knobs as `[Property]` fields** on a Component — e.g.
   `bool AgentControlled`, `Vector3 AgentTarget`, `float AgentSpeed`,
   `float AgentStopRadius`. In `OnUpdate`, if `AgentControlled`, run a
   per-frame `AgentTick()` that walks the `Rigidbody` toward `AgentTarget`,
   faces the heading, stops within `AgentStopRadius`, and logs progress
   once per second with a distinctive prefix (e.g. `[AgentDrive]`).
2. **Find the body at runtime** — MCP `find_game_objects` by name returns
   the GameObject id; `get_game_object` with `includeComponentProperties=true`
   returns component ids and current property values.
3. **Drive it** — MCP `set_component` with the component id (or game object
   id + type name) and a properties JSON object updates `[Property]` fields
   live during play mode. Example:
   `set_component { id: "<LuteBuilderNpc id>", properties: { "AgentControlled": true, "AgentTarget": "0,400,2", "AgentSpeed": 393.7 } }`
4. **Read the result** — `read_console` with `filter:"AgentDrive"` shows
   pos/dist/grounded/vel each second; `get_game_object` re-queries the
   world position to confirm movement. `scene_trace` casts rays to inspect
   nearby geometry the body is approaching.
5. **In-game chat from user to agent** — `LuteAgentChat.razor` (key J, not
   F6 which is S&Box's record shortcut) logs user messages as
   `[AgentChat]` lines via `Log.Info`. The agent polls
   `read_console` with `filter:"AgentChat"` and a `since` cursor to pick up
   new messages. No disk writes — `File.AppendAllText` is rejected by the
   S&Box whitelist.

**MCP tool invocation note**: the native server exposes a meta-tool API —
`search_tools` (find tools by keyword), `call_tool` (invoke by name),
`list_toolsets`/`describe_toolset`, plus directly-callable tools like
`editor_status`, `read_console`. Use `search_tools` with a keyword query to
discover scene/play/trace/asset tools, then `call_tool` or the tool's own
endpoint to invoke. `read_console` returns a `since` cursor — pass it back
on the next call to get only new entries.

## Conventions

- Engine: S&Box (Source 2), C# .NET 10, `Sandbox` namespace,
  `RootNamespace=Sandbox`.
- All gameplay code lives in `sbox/code/`. Do not mix Godot/GDScript or
  Unreal C++ into this project (both were migrated away from — see git
  history "Migrate from Godot/Unreal to S&Box").
- Materials/textures/models are Source 2 binary formats (`.vmat_c`,
  `.vtex_c`, `.vmdl_c`) under `sbox/.sbox/cloud/` and `sbox/Assets/`. Don't
  reference Godot `.tres`/`.tscn` or Unreal `.uasset` paths.
- Prefer `Log.Info`/`Log.Warning` for diagnostics — these show up in the
  editor log that `sbox_verify.ps1` reads.
- Server-authoritative design per PRD §5.1: world state, soul status,
  economy, and quest generation belong server-side; client code is input/
  prediction/HUD only. Not yet enforced in code (single-player scaffolding
  so far) — apply `[Sync]`/`[Broadcast]`/`Host.IsServer` when multiplayer
  features are added.
